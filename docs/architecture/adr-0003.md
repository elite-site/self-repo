# ADR-0003 — Prisma track migrations from the start

## Status

Accepted. Decided 2026-09-20.

## Context

In the previous project the production schema drifted from the codebase because it
was applied via `prisma db push`, which writes whatever the current schema file
declares without any migration history. That made environments unreproducible and
removed any ability to review what changed before it hit production.

## Decision

Track schema changes as first-class migrations from the start. Baseline is created
with `prisma migrate dev` and committed as SQL under
`backend/prisma/migrations/` (starting with the initial migration
`20260920055533_init`). Releases apply them with `prisma migrate deploy`, never
`db push`. A migration check is part of CI: the schema and migration history must
be in sync before a release is allowed.

## Consequences

- Environments are reproducible: any fresh Supabase instance reaches the intended
  schema by replaying committed SQL.
- Schema changes are reviewable like any other diff, and rollback points exist in
  the migration history.
- Adding a migration gate to CI means a forgotten `migrate dev` step fails the
  build instead of silently starting prod drift again.
- A developer must remember to run a migration locally when the schema changes,
  or the CI gate catches them.
